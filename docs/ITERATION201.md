# Iteración 2.101: clases RTTI resuelven el dispatch de actualización del manager

La inspección del PE original 2009 ya no deja las direcciones `0x47ee10` y `0x481040` como referencias anónimas. La sonda [`x86_replay_manager_vtable_probe.py`](../tools/x86_replay_manager_vtable_probe.py), fijada al SHA-256 `24e6149f729047fb3f5ceb24c8cdc055de2d1547babaa6724e0d6eba4530ded3`, lee Complete Object Locator, TypeDescriptor y Class Hierarchy Descriptor de MSVC, verifica entradas y constructores, y guarda `artifacts/kernel/replay-manager-vtable-original-2009.json`.

El slot 16 (`+0x40`) de `CBattleManager` (`0x8218e4`) apunta a `0x481040`. `CBattleManagerStory` (`0x82192c`) deriva de `CBattleManagerBase` y reemplaza el slot 16 por `0x47ee10`; sus constructores escriben esa vtable en `0x437918` y `0x43b488`. `CBattleManagerArcade` (`0x821994`) deriva de `CBattleManager` y conserva `0x481040` en ese slot; su constructor lo escribe en `0x438a4e`. Se confirmaron además los slot 5 de estas tablas: el método Story `0x47f810` llama al slot 16 de la vtable del mismo objeto (`0x47f82e`), mientras base/Arcade usan `0x481690` con el mismo despacho virtual. Esto conecta el flujo de actualización Story con el override `0x47ee10`.

Así, para una instancia de manager Story, ese despacho virtual concreto selecciona `0x47ee10`; no selecciona simultáneamente el método base/Arcade `0x481040`. El replay del usuario está almacenado bajo `replay/story`, lo que hace que esa ruta sea relevante, pero el análisis estático no prueba qué constructor usa la sesión al reproducirlo ni excluye que otro objeto alcance el otro callback. Tampoco establece una llamada por frame: `0x47ee10` llama al decoder `0x42a410` en modo global 2, y falta determinar el estado de fuentes `this+0xf0`, el consumo efectivo del cursor y su relación con el tick. No se implementó cadence ni se modificó el runtime.

La regresión nueva `tests/test_replay_manager_vtable_probe.py` corre junto a dispatch/layout: 12 pruebas pasaron. El intento de inspección UI en esta sesión no llegó al juego; el runtime de automatización falló al inicializar por kernel assets no encontrados. Próximo análisis estático: seguir los constructores/clase global `0x85eb64` y el estado de fuentes que permite a `0x42a410` consumir el vector; luego volver a medir una ventana con frame-step cuando el control soportado del escritorio esté disponible.
