# Iteración 2.100: cursor C por parejas validado con el replay real en Vita3K

El decoder original `0x42a410`, con ambos flags de fuente activos (`this+0xf0 == 3`), consume dos words en una invocación: el primero actualiza la máscara baja y seis IDs de input; el segundo solo actualiza la máscara baja del otro canal. Añadí `t123_replay_next_input_pair()` para representar esa unidad en el core C. La función prepara una copia del cursor y publica cursor/resultados solo cuando puede leer los dos words; si queda un word huérfano, falla sin consumirlo. No supone que una pareja corresponda a un frame.

El script manual Vita ahora incorpora `src/replay.c` en `libt123_core.a`; CMake ya lo compilaba. El contrato C de parejas comprueba mapeo, avance de dos words y fallo atómico ante un vector impar. Se compiló un test Vita que abre el archivo real desde `ux0:data/Touhou123Vita/replay/story/090815_2219_sanae_story.rep`, valida versión `0x100c8`, los personajes `(15,16)`, `(15,17)`, `(15,0)`, y recorre las 4,360, 3,466 y 9,084 parejas esperadas. Vita3K lanzó los VPK de contrato sintético y real en una instancia temporal aislada; ambos terminaron con código 0 y el log real confirma la apertura del `.rep` desde `ux0:data`.

El replay conservó su hash SHA-256 `6905658c1f5fb09089eecd5d5b7323f581b4b2030293f27c0323dafb9895de3`. El VPK de contrato usa solo el test y el parser, sin recursos del juego. El gate prueba el parser y el consumo de parejas con el archivo real, no reproduce la pelea ni valida correspondencia con frames/ticks, asignación de los dos canales a controladores o la ruta de sincronización `0x4600fe`. Por eso el cursor todavía no se conecta al combate del juego.
